# G-market Growth Radar — контекст проекта

## 1. Цель

Создать отдельный внутренний web-сервис, который автоматически объединяет:

1. фактическое содержимое интернет-магазина;
2. техническое состояние страниц;
3. поисковый спрос из Яндекс Вебмастера;
4. поведение пользователей из Яндекс Метрики;
5. дополнительные бизнес-данные из Excel;
6. автоматические сигналы и Opportunity Score;
7. AI-анализ наиболее перспективных точек роста.

Главный вопрос системы:

> Где интернет-магазин сейчас недополучает потенциальный целевой трафик или продажи и что имеет смысл изменить в первую очередь?

Система должна сокращать тысячи URL и поисковых запросов до нескольких приоритетных действий.

---

## 2. Формат решения

Это отдельный локальный/internal web-проект.

Рабочая версия должна уметь запускаться:
- локально;
- в Docker;
- впоследствии на внутреннем сервере компании.

Целевой интернет-магазин доступен из корпоративной подсети.

Growth Radar должен самостоятельно сканировать сайт по HTTP/HTTPS из той же сети.

---

## 3. Источники данных

### Интернет-магазин
Система сама сканирует сайт:
- sitemap;
- robots.txt;
- внутренние ссылки;
- отдельные seed URL.

### Яндекс Вебмастер
Подключение по официальному API через OAuth.

Нужно получать поисковые данные:
- URL;
- запрос;
- показы;
- клики;
- CTR;
- среднюю позицию;
- дату;
- регион, если доступен.

### Яндекс Метрика
Подключение по официальному API через OAuth.

Нужно получать агрегированные данные поведения:
- визиты;
- посетители;
- просмотры;
- отказы;
- среднюю длительность;
- достижения выбранных целей.

### Excel
Дополнительные бизнес-данные загружаются пользователем вручную в XLSX.

Прямых интеграций с 1С, ERP или CRM нет.

### CRM
CRM вообще не является источником проекта.

Не проектировать CRM-интеграцию.

---

## 4. Что система НЕ должна делать

Первая версия не является:
- CRM;
- ERP;
- CMS;
- заменой Метрики;
- заменой Вебмастера;
- полноценным Screaming Frog;
- системой автоматического редактирования сайта;
- системой автопубликации;
- системой автоматической постановки задач;
- генератором SEO-статей.

Сначала система только анализирует, приоритизирует и рекомендует.

---

## 5. Главный продуктовый принцип

Нельзя делать еще один тяжелый BI.

Ценность продукта:

```text
тысячи страниц и запросов
        ↓
сбор и нормализация данных
        ↓
10–20 значимых сигналов
        ↓
TOP-5 возможностей
        ↓
объяснение причины
        ↓
конкретное действие
        ↓
измерение результата
```

Если новая функция не помогает этому циклу, ее не добавлять без необходимости.

---

## 6. Правило реализации

После каждого спринта:

1. production build;
2. typecheck;
3. tests;
4. проверка миграций;
5. обновление README;
6. отдельный `SPRINT_N_RUNBOOK.md`;
7. список известных ограничений;
8. переход к следующему спринту только после acceptance.

Все изменения БД делать только через миграции.

Destructive migrations запрещены без отдельной явной процедуры резервного копирования.

Секреты и OAuth tokens никогда не должны попадать во frontend или application logs.
