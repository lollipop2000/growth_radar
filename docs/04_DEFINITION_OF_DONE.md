# G-market Growth Radar — ограничения и Definition of Done

## 1. Что сознательно НЕ делать в первых спринтах

Не реализовывать:
- CRM;
- прямую интеграцию 1С;
- ERP integration;
- изменение контента сайта;
- автопубликацию;
- генерацию SEO-статей;
- автоматическую постановку задач;
- email-рассылки;
- Telegram;
- мобильное приложение;
- сложную RBAC;
- конкурентный SEO-анализ;
- парсинг Яндекс SERP;
- Google Search Console;
- рекламу;
- сквозную атрибуцию;
- Data Warehouse;
- ML forecasting;
- автоматическую оценку денег от каждой рекомендации.

Сначала доказать пользу Radar.

---

## 2. Definition of Done MVP

Проект достиг цели, если на реальном интернет-магазине из корпоративной сети пользователь может:

1. указать URL сайта;
2. просканировать сайт;
3. получить список страниц и их характеристики;
4. подключить Яндекс Вебмастер;
5. подключить Яндекс Метрику;
6. автоматически связать данные по URL;
7. загрузить Excel с дополнительными бизнес-данными;
8. получить рассчитанные Opportunities;
9. увидеть TOP-5;
10. понять, почему каждая Opportunity появилась;
11. запустить AI-анализ;
12. получить максимум три обоснованные гипотезы;
13. принять одну гипотезу в работу;
14. отметить дату изменения;
15. впоследствии сравнить показатели до и после.

---

## 3. Главная продуктовая проверка

После открытия Growth Radar пользователь должен максимум за несколько минут понять:

> В какие 3–5 точек интернет-магазина сейчас разумнее всего вложить усилия?

Если для ответа приходится вручную изучать десятки графиков, продуктовая задача не решена.

---

## 4. Критерии качества данных

Система должна явно показывать:
- свежесть каждого источника;
- unmatched URLs;
- ошибки sync;
- ошибки crawler;
- отсутствующие данные;
- источник каждого вывода.

Opportunity без evidence недопустима.

AI-гипотеза без evidence недопустима.

---

## 5. Критерий архитектурной простоты

Не добавлять инфраструктурные компоненты только ради "правильной архитектуры".

Предпочтение:
- PostgreSQL вместо нескольких хранилищ;
- cron/jobs вместо сложной очереди;
- обычный HTTP crawler вместо Playwright;
- rule engine вместо LLM, если задачу можно выразить формулой;
- LLM только для объяснения и гипотез.

---

## 6. Критерий безопасности

Нельзя:
- логировать OAuth tokens;
- отдавать secrets в frontend;
- отправлять токены в LLM;
- без ограничений сканировать production;
- автоматически менять сайт;
- автоматически публиковать рекомендации.

---

## 7. Критерий приемки каждого спринта

Каждый Sprint закрывается только после:
- production build PASS;
- typecheck PASS;
- tests PASS;
- migration check PASS;
- ручного acceptance;
- обновления README;
- создания `SPRINT_N_RUNBOOK.md`;
- фиксации известных ограничений.
