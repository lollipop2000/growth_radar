# Sprint 3.3 — Commerce Growth Radar

## Status

Реализован Sprint 3.3. Sprint 4–5 не начаты; LLM и новые внешние интеграции отсутствуют. Расчёт работает по подтверждённым BusinessRecord, существующим Page и накопленной Метрике/Вебмастеру. Производственные Scanner, Metrika sync и Webmaster export не запускаются.

Техническая, локальная DB/UI приёмка проходит без Webmaster. Production-расчёт не подтвердил коммерческие growth/risk сигналы при текущем покрытии: обнаружены сигналы качества данных. Это ограничение реальных файлов, а не зависимость Commerce Engine от Search.

## Commercial Data Model

Иммутабельная история Import/BusinessRecord сохраняется. ProductGroup и SKU представлены актуальным реестром MAPPING, коммерческий профиль страницы вычисляется из него; дублирующая таблица каталога не нужна. `PreparedPage.commerce` содержит группы, SKU, остатки, цены, продажи, эффективность, динамику, свежесть, полноту и benchmarks.

Additive миграция `202610060003_commerce` добавляет в Opportunity nullable searchScore/commerceScore/overallScore, domain и primaryType. Прежний score хранит итог для совместимости сортировки. История миграций и старые evidence snapshots не переписаны. Identity прежняя: site/page/rule/period. DISMISSED сохраняется; неподтверждённые результаты получают isCurrent=false, а не удаляются.

## SKU → ProductGroup → Page aggregation

Последняя подтверждённая версия каждого SKU определяет группу и URL. Используется существующий URL matcher, включая aliases. Коммерческие записи привязываются при чтении через актуальный маппинг, даже если их старый pageId отсутствует. Неактивные связи исключены; конфликт нескольких Page у одной группы исключается из расчёта, без произвольного выбора.

Все группы одной Page и все их активные SKU входят в профиль. Остатки выбираются по последней дате SKU, затем последней загрузке каждой комбинации склад/регион/единица. Склады суммируются только в сопоставимых единицах. Старые измерения не воскресают после нового snapshot. Будущие даты не используются.

Продажи выбираются по последнему import для SKU/даты. Суммы orders/quantity/quantityKg/revenue не умножаются повторными загрузками. Наблюдаемые суммы могут быть частичными: отсутствие SKU не означает нулевых продаж. Сильные правила требуют достаточного покрытия каждого SKU. Неизвестный показатель в наблюдаемой строке остаётся неизвестным.

Цены: latest snapshot по SKU и типу/валюте, min/max и невзвешенное среднее по SKU. Несопоставимые валюты не конвертируются. Несколько типов цен отключают ценовые выводы. Аномалия проверяется внутри одного группового кода, не между разными группами на одной Page.

## Commerce Metrics

По умолчанию текущие 28 полных дней МСК и предыдущие 28. UI поддерживает 7/28/30/90. Сегодня не включается в продажи/трафик периода; актуальное состояние остатков/цен может иметь сегодняшнюю дату.

- Визиты, сумма дневных visitors; visitors не являются уникальными людьми за весь период.
- SUM orders, quantity, quantityKg, revenue по связанным SKU.
- Цена min/max/average; средняя предыдущего периода — по дням с наблюдаемым состоянием, с переносом последней известной цены вперёд, без заполнения назад.
- Остаток, единица, stockKg только при явно указанной единице кг; детализация SKU и даты.
- Revenue/visit, kg/visit, orders/100 visits, revenue/order, kg/order. Нулевой знаменатель даёт неизвестное значение.
- Изменения визитов, выручки, кг, заказов и цены; изменение запаса при известной истории.

Покрытие продаж — минимум наблюдаемых дней среди всех SKU группы. Порог достаточности default 75%. Разреженная транзакционная выгрузка не доказывает нулевые продажи в отсутствующие дни. Для нулевых продаж нужны явные нулевые строки каждого SKU и даты. Сравнения не используют несопоставимые периоды.

## Days of Stock

`stockKg / (quantityKg / число дней с данными)`. Требуются актуальные остатки, свежие продажи, достаточное покрытие и положительные кг продаж. Нет кг, нулевые продажи, устаревший/неполный остаток или неизвестная единица → «Нет данных». Литры и штуки автоматически в кг не переводятся.

Зоны default: <7 критический риск; 7–14 риск; >14–60 нормальный; >60–90 повышенный; >90 избыточный. Непрерывные границы учитывают дробные дни. Пороги настраиваются; это эвристика.

Остатки >2 дней, цены >7 дней, продажи >3 дней считаются устаревшими. Дата свежести страницы берётся консервативно по старейшему состоянию SKU; частичное наличие явно показано. Для stale сигналов требуется известная устаревшая дата, пропуск не выдаётся за старую дату.

Benchmarks исключают саму страницу, требуют default 5 peers: категория+page type → page type → сайт. Медианы visits/revenuePerVisit/kgPerVisit/ordersPer100 и revenue/P80 используют только свежие, достаточно полные данные. При недостатке peers сравнение недоступно.

Пороги редактируются в существующих настройках правил на `/opportunities`: visits/revenue/kg, stock zones, highStockKg, trafficGrowth/salesDecline/priceGrowth/efficiencyGap/priceRatio, freshness и minPeers. Старые Search thresholds сохранены.

## Commerce Score

Отдельные компоненты: объём 20, трафик 15, эффективность 20, запас 20, динамика 15, приоритет 10. Объём использует выручку относительно max(minRevenue,P80), кг относительно minKg и заказы относительно 10. Эффективность учитывает относительное отставание либо преимущество от медианы. Запас — дефицит либо избыток; известный нулевой запас даёт 20. Динамика — абсолютное изменение относительно порога. Без приоритета используются нейтральные 50/100.

Все формулы и доступные веса хранятся в scoreBreakdownJson и показаны в detail. Недоступный/устаревший источник исключается из соответствующего сильного компонента, без подстановки нулевого результата. Score не является прогнозом выручки или доказательством проблемы.

## Overall Score

Commerce Score = 100 × сумма доступных баллов / сумма доступных весов. Для Commerce signal Overall — среднее доступных Commerce/Search блоков с весами их доступных компонентов. Отсутствующий Search не добавляет нулевой вес: Overall равен Commerce Score и может превышать 90. Для Search rules сохранена прежняя оценка, Commerce хранится отдельно. Раздельные Search/Commerce/Overall показаны в detail; поисковый блок и его формулы раскрыты при наличии.

Domain: SEARCH, COMMERCE, DATA_QUALITY; primaryType: SEARCH, GROWTH, RISK, DATA_QUALITY. Подписи карточек позволяют отличить качество данных от роста и риска.

## Known Limitations

- Транзакционные продажи редкие и не имеют явной декларации полноты выгрузки. Нельзя автоматически считать отсутствующие дни/SKU нулевыми: правила сравнения и отсутствия продаж консервативно выключены.
- Остатки загружены в штуках и иных/неуказанных единицах. Без явно указанного веса или согласованного коэффициента запас в днях неизвестен. Вес не выводится из названия товара.
- Несколько типов цен, разные валюты, отсутствие предыдущей истории отключают ценовые сравнения. Среднее не взвешено оборотом. Наблюдение цены и продаж не доказывает причинность.
- Известный положительный остаток в конце предыдущего периода не доказывает непрерывное наличие весь период; RULE 17 остаётся гипотезой.
- Отсутствующие ранее достижения целей Метрики не восстанавливаются. Старые ограничения WAF/Вебмастера и приложения без RBAC сохраняются.
- Исторические неактивные связи SKU исключаются из текущего профиля. Для исторического маппинга на дату продажи потребуется отдельный согласованный контракт.
- Синхронный bulk dataset рассчитан на текущий каталог, не на миллионы строк. Docker image в этой приёмке не публиковался.

Изменения: `src/lib/opportunities/{commerce,commerce-rules,commerce-score,dataset,model,aggregate,service,rules/index}.ts`, коммерческий компонент и существующие Dashboard/Opportunities/Page 360/Business Data, quality helper, локализация/CSS, Prisma migration и локальные acceptance scripts/tests. Scanner и Yandex transport/queue logic не изменены.
