## Sales Import Modes

Import хранит `salesImportMode`: UNKNOWN, PARTIAL, TRANSACTIONAL. Миграция назначает существующим файлам UNKNOWN, сохраняя консервативную семантику. Режим не определяется по строкам или имени файла. `/business-data` предлагает явный выбор; сохранённый профиль может задать тип при следующей загрузке. Период из профиля не переносится: пользователь подтверждает даты нового файла.

## Transactional Semantics

Для актуального активного SKU, связанного с Page без конфликта группового кода, отсутствующий SKU/день внутри подтверждённого TRANSACTIONAL import логически имеет orders/quantity/quantityKg/revenue = 0. Физические нулевые BusinessRecord не создаются. Пустая ячейка существующей строки остаётся unknown. PARTIAL и UNKNOWN не утверждают полноту пропущенных дат/SKU.

Для каждого SKU/дня используется наиболее свежий подтверждённый import по finishedAt (createdAt при отсутствии finishedAt), затем ID для стабильного разрешения равенства. Транзакционный файл участвует и без строки; PARTIAL — только для содержащихся строк. Более свежий транзакционный ноль заменяет прежние продажи, а пустой PARTIAL не стирает старый полный источник. При перекрытии разные дни могут иметь разные источники. Provenance сохраняет importId, mode, coverageFrom/To, selectedDays и zeroFilledDays.

Учитываются только подтверждённые импорты текущего Site. SKU, отклонённые из исходного файла и впоследствии добавленные в mapping, исключаются из zero-fill этого файла. Изменение бизнес-данных во время Rules recalculation выявляется под существующим advisory lock; требуется повторный пересчёт.

## Coverage Period

`coverageFrom` и `coverageTo` — nullable DATE; для TRANSACTIONAL обе даты обязательны, валидны, начало не позже окончания, строки файла внутри периода. Для расчётного окна 7/28/30/90 дней применяется пересечение с заявленным периодом. Транзакционные сильные выводы требуют покрытия каждого дня этого окна по каждому SKU. Дни за границами coverage неизвестны.

Настройка метаданных старого SALES import доступна только для выбранного Site и завершённого импорта. Повторная проверка исходного листа блокирует объявление полноты при ошибочных строках известных SKU или изменении состава принятых строк. Unknown SKU явно исключены; остальные ошибки нужно исправить и переимпортировать файл либо оставить PARTIAL. BusinessRecord при редактировании метаданных не меняются. Пустая корректная транзакционная выгрузка с заголовками и явно подтверждённым периодом допустима.

## kgPerUnit

Nullable `BusinessRecord.kgPerUnit` DECIMAL(18,6), только явная колонка «Кг в единице SKU» в mapping. Значение положительное, минимум 0,000001 кг, максимум менее 10^12. Последняя версия маппинга каждого SKU определяет коэффициент; при загрузке новой версии без значения коэффициент неизвестен. Ведущие нули SKU остаются текстом.

Статический `public/templates/product_mapping_template.xlsx` содержит рекомендуемую колонку и пример SKU 100001 с 180 кг/ед. Это пример, не production-коэффициент. Лист «Описание» объясняет перевод остатков и запас в днях. `sales_template.xlsx` объясняет транзакционные нули; примерная строка остаётся одной фактической продажей.

## Stock Conversion

Для строки в кг значение используется напрямую; для шт/шт./pcs — stock × явный kgPerUnit. Другие и неизвестные единицы не конвертируются. Выбирается последняя дата остатка SKU, внутри неё последние версии склад/регион/единица; будущие даты исключены. Если часть вкладов одного SKU неизвестна, его stockKg неизвестен.

Page/groupStockKg — сумма известных вкладов SKU, либо unknown при отсутствии известных вкладов. `stockKgCoverage` = число SKU с известным stockKg / число активных SKU. Частичная сумма показывается вместе с покрытием. Сильные правила и компонент Stock Risk требуют достаточного покрытия и свежести. `minStockKgCoverage` по умолчанию 1 (100%), настраивается в порогах. Правило отсутствия товара также допускает подтверждённый нулевой stockUnits по всем SKU в штуках без коэффициента. Свежесть и полнота снимков сохраняются отдельными проверками.

## Days of Stock

averageDailySalesKg = quantityKg / число покрытых дней расчётного периода. Для полного транзакционного окна знаменатель — все дни окна, включая логические нули. Для старых неполных выгрузок сохраняется прежняя консервативная проверка покрытия и наблюдаемых дней.

daysOfStock = stockKg / averageDailySalesKg; нужны свежие полные продажи, достаточно свежих остатков с покрытием, положительные средние продажи. Нулевые продажи не дают infinity. При stockKg > 0 UI показывает «Продаж за период нет». Page 360 и Opportunity Detail показывают формулу, коэффициенты SKU, coverage, даты и provenance. Транзакционный источник сопровождается текстом «Отсутствие транзакций внутри периода трактуется как 0 продаж».

## Rule Changes

- RULE 11: достаточно визитов, полное покрытие всех дней/SKU, revenue/kg/orders известны и все равны нулю.
- RULE 12: свежий реальный stockKg, coverage, подтверждённые продажи и низкий daysOfStock.
- RULE 13: известный нулевой stockKg при достаточном покрытии либо нулевой stockUnits в штуках по всем SKU.
- RULE 14: большой stockKg + низкие продажи/высокий daysOfStock; отдельный путь при quantityKg = 0 без бесконечности.
- RULE 15–19: сравнения используют новую агрегацию; 0 → 0 — отсутствие роста, рост с 0 не считается стагнацией, сохраняя полноту/свежесть, traffic coverage, медианы и ценовые ограничения.
- RULE 20: прежнее сравнение сопоставимых свежих цен внутри группы.
- RULE 21: прежние freshness thresholds, отдельный DATA_QUALITY.
- RULE 22: высокий revenue/P80 + низкий реальный daysOfStock.

## Commerce Score

Stock Risk использует доступный конвертированный stockKg и достаточное покрытие, включая нулевые продажи при большом запасе. Efficiency/Trend используют подтверждённые полные продажи и прежние условия сравнения. Отсутствующие компоненты остаются null, оценка нормализуется по доступному весу. DQ score сохранён только для сортировки качества данных и исключён из основного TOP.

## User Actions — что должен сделать пользователь

1. Открыть `/business-data` и проверить текущий маппинг.
2. Загрузить обновлённый mapping с подтверждённой массой каждой учётной единицы в колонке «Кг в единице SKU»; проверить предпросмотр и подтвердить.
3. Открыть завершённый импорт продаж из истории → «Настроить тип выгрузки» либо загрузить новый файл.
4. Выбрать «Транзакционная выгрузка» только если файл действительно содержит все продажи выбранного Site за заявленный период; подтвердить обе даты. Проверить неизвестные SKU/ошибки, исправить известные ошибочные строки переимпортом.
5. Сохранить настройки и открыть Opportunities → выбрать период → «Пересчитать возможности».
6. Проверить coverage, формулу и provenance в Page 360/Opportunity Detail. Метаданные сами не запускают пересчёт или jobs.

## Known Limitations

- Полнота транзакционного файла — явное утверждение пользователя; приложение не может проверить полноту 1С. Научная оценка причинности/прогнозы не добавлены.
- Старые файлы UNKNOWN и коэффициенты неизвестны до действий пользователя. Реальные Growth/Risk и days могут оставаться отсутствующими.
- Исторические SKU оцениваются через текущий mapping; исторический mapping на дату продажи не реализован.
- Файл продаж сохраняет прежний ключ SKU/дата: несколько транзакций одного SKU за день нужно агрегировать до загрузки. Нулевые ячейки можно задать явно; пустые не заменяются нулём.
- Заказы суммируются по SKU, поэтому один заказ нескольких товаров может учитываться несколько раз. Валюты не конвертируются, цены не взвешиваются оборотом.
- Неполный остаток в кг показывает только известную сумму; правила с покрытием ниже 100% требуют осознанной настройки порога.
- Нет RBAC; приложение предназначено для localhost/доверенной сети. Sprint 4/5, новые crawler/integration/автоматические задачи не реализованы.
