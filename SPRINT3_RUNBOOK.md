## Excel Import

`/imports` → загрузить файл → выбрать лист → просмотреть первые 20 строк → сопоставить колонки → проверить строки → подтвердить импорт. До подтверждения BusinessRecord не создаются. После проверки показываются валидные, пропущенные и ошибочные строки; mapping и форматы доступны для проверки. Изменение mapping требует повторной проверки. Ошибки строк не отклоняют остальные записи.

Поддерживаются XLSX и существующий формат CSV UTF-8 с запятой/точкой с запятой. XLS не поддерживается. Ограничения: 5 МБ исходного файла, 20 МБ распакованного XLSX/сохранённых значений, 1000 ZIP entries, 20 листов, 100 колонок и 10 000 строк на лист. Не выполняются формулы, макросы, скрипты, внешние ссылки и запросы. Строка с формулой отклоняется, даже если формула имеет cached result. Импортируются только значения; гиперссылка не открывается. Показывается не более 100 сообщений ошибок, полный счётчик сохраняется.

Необязательные поля: URL, SKU, название товара, категория, товарная группа, бренд, цена, остаток, наличие, упаковка, приоритет, дата, заказы, количество кг, выручка. Сопоставить нужно хотя бы URL или SKU. Неизвестные колонки сохраняются в attributesJson без интерпретации. Цена/выручка имеют Decimal(18,4); числовые значения неотрицательны, приоритет 0–100. Форматы чисел: русская запятая либо точка; форматы дат: ISO, день/месяц/год, месяц/день/год. Поддерживаются настоящие Excel dates/serial dates. Неоднозначные/невозможные даты отклоняются.

URL проходит прежний normalizeUrl и matchUrl: точный нормализованный адрес либо подтверждённый однозначный redirect alias. Значимые query params сохраняются, canonical не создаёт новую связь. Неизвестный URL и запись только с SKU остаются несопоставленными. SKU не угадывается по странице. Бизнес-импорт не создаёт Page и не сканирует URL. История не удаляется, повторное подтверждение одного draft идемпотентно.

## Import Profiles

При проверке указать имя профиля; он сохраняется при подтверждении импорта. Следующая загрузка: выбрать профиль и нажать «Применить профиль». Подставятся лист, mapping, формат дат и чисел. Профиль хранит имена исходных колонок; при изменении порядка колонок сопоставление восстанавливается по уникальным именам. Отсутствующие/неоднозначные колонки нужно сопоставить вручную. Выбор другого листа доступен отдельно.

## Business data model

- Import: сайт, файл/размер, лист/профиль, draft значений, mapping, статус, timestamps, total/imported/skipped/errors/matched/unmatched.
- ImportProfile: сайт, уникальное имя, лист, mapping с исходными заголовками, форматы, createdAt/updatedAt.
- BusinessRecord: import/строка, nullable Page, URL/SKU, перечисленные бизнес-поля, attributesJson, matchStatus. Уникальная пара importId/rowNumber.
- Opportunity: сайт/Page/rule/период, score/severity, русский текст, evidence и breakdown snapshots, ACTIVE/DISMISSED, isCurrent, timestamps.

Новая загрузка сохраняет историю. Для расчёта продаж по Page/date выбирается последняя выгрузка, затем суммируются строки этой выгрузки: повторный upload не умножает продажи. Недатированные продажи не участвуют в сравнении периодов. Последние непустые коммерческие значения сохраняют ранее импортированные поля при частичной новой выгрузке. Нет SKU cross-page aggregation. Главная показывает продажи только сопоставленных записей и явно это поясняет.

## Rules Engine

`src/lib/opportunities/` отдельно от React: подготовка dataset, агрегаты, pure rules, score, persistence. `rules/index.ts` содержит десять отдельных функций правил, принимающих PreparedPage/Dataset и возвращающих факты либо null. Общий результат — signal с ruleId/pageId/severity/rawScore/title/description/evidence/period/createdAt. rawScore отражает уровень сигнала; в итоговом score нет скрытого множителя на правило или severity.

Подготовка данных выполняет несколько bulk reads по сайту, активному счётчику/host и двум периодам; нет SQL-запроса метрик на каждую страницу. Последняя попытка Scanner отделена от последнего успешного содержимого. HTTP/BROWSER/IMPORT используются одинаково. Старые неверные подключения счётчика или другого сайта не смешиваются с текущими.

Пересчёт: `/opportunities`, период по умолчанию 28 полных дней по Москве и предыдущие 28; также 7/30/90. День сегодня исключён. Нет автоматического пересчёта. Адреса в scanner очередях и настройки Яндекса расчёт не меняет.

Identity Opportunity: site + page + rule + periodFrom + periodTo. Повторный расчёт обновляет score/evidence, сохраняет DISMISSED. Неподтверждённые последним расчётом сигналы получают isCurrent=false, история доступна по прежнему detail URL. Advisory lock сериализует публикацию расчёта и изменение порогов. Изменение порогов во время подготовки dataset отклоняет устаревший расчёт.

## Реализованные правила

| Правило | Условие | Production signals |
| --- | --- | ---: |
| 01 | Показы ≥ минимум, известная позиция и CTR существенно ниже сравнения своего диапазона | 0 |
| 02 | Показы ≥ минимум, позиция в настраиваемом диапазоне 5–15 | 1 |
| 03 | Визиты ≥ минимум, известные выбранные цели и конверсия ниже медианы | 3 |
| 04 | Показы снизились на порог при достаточном покрытии обоих периодов | 0 |
| 05 | Позиция ухудшилась при стабильных показах и сопоставимых периодах | 0 |
| 06 | Показы выросли на порог при сопоставимых периодах | 0 |
| 07 | Поисковый спрос + подтверждённые 404/410/5xx/noindex/canonical/redirect issue | 0 |
| 08 | Поисковый спрос + отсутствующий заголовок/описание/основной заголовок | 0 |
| 09 | Спрос либо трафик + подтверждённое Excel отсутствие/нулевой остаток | 0 |
| 10 | Продажи снизились при стабильном поиске/визитах и сопоставимых датированных бизнес-периодах | 0 |

WAF/403, авторизация, network/timeout не считаются SEO-ошибкой страницы. Отсутствующий canonical не является проблемой. Canonical сравнивается прежним normalizer с фактическим final URL. Текст менее 100 слов отмечается как дополнительный факт только вместе с отсутствующими on-page элементами; сам по себе не создаёт возможность.

Для правил сравнения нужны ≥75% дней с наблюдаемыми данными в каждом периоде. Отсутствующие даты не подменяются нулями. Это консервативный подход: редкая поисковая статистика может не дать сигнал даже при реальном изменении. Продажи с отсутствующими значениями не считаются нулевыми. Стабильность подтверждается по поиску либо визитам с достаточными данными.

## Пороги, CTR и conversion benchmark

Пороги сохраняются в Integration типа `Rules Engine:<siteId>` отдельно от Яндекса. UI: раскрыть «Настройки правил и формулы». Defaults: минимум 100 показов/100 визитов; позиции 5–15; отставание CTR 0,30; отставание конверсии 0,50; рост/падение 0,30; ухудшение позиции 2 пункта; допуск стабильности ±0,20; покрытие дат 0,75; шкала спроса 10 000 показов. Доли 0–1 явно подписаны.

CTR RELATIVE по умолчанию: диапазоны ≤3, >3–5, >5–10, >10–20, >20. Нужно минимум две страницы с достаточными показами в диапазоне. CTR сравнения = 100 × SUM(clicks)/SUM(impressions), не среднее CTR строк. При недостатке peers сравнение отсутствует и правило 01 не срабатывает. SIMPLE использует явно выбранный пользователем CTR (редактируемое поле; default 2%), без универсального автоматически применяемого CTR=3%.

Конверсия = 100 × сумма достижений выбранных Primary Goals / visits. Если хотя бы выбранная цель отсутствует в данных, конверсия неизвестна. Benchmark — медиана минимум пяти страниц того же сохранённого типа, иначе медиана минимум трёх страниц всего, с достаточным трафиком и известными целями. Нулевая медиана не создаёт утверждение о низкой конверсии. Это сумма достижений, не доля уникальных покупателей; цели могут пересекаться. Используется существующая Page classification: её точность влияет на peers.

## Opportunity Score и breakdown

Все формулы и доступные/недоступные компоненты сохранены и показаны в detail.

| Компонент | Вес | Формула |
| --- | ---: | --- |
| Поисковый спрос | 30 | 30 × min(1, ln(1+показы)/ln(1+шкала спроса)) |
| Потенциал позиции | 20 | В диапазоне: 20 × (1 − 0,75 × (позиция−нижняя граница)/max(1,ширина)); вне диапазона 0 |
| Потенциал CTR | 20 | 20 × max(0,1−CTR/benchmark); при нулевом benchmark 0 |
| Потенциал конверсии | 15 | 15 × max(0,1−conversion/median); при нулевой медиане 0 |
| Бизнес-приоритет | 15 | 15 × priority/100; отсутствующий priority = нейтральные 50 |

Итог = SUM(доступных баллов) × 100 / SUM(доступных весов), bounded 0–100. Отсутствующие показатели исключены, а отсутствие Excel не штрафуется. UI отмечает неполные данные. 75 по двум доступным компонентам не означает вероятность роста на 75% или полный набор источников. При одних нейтральных бизнес-баллах score=50; отсутствие данных само по себе не создаёт signal.

## Известные ограничения

- Excel пользователя ещё не загружен; правила 09–10 не дают production signals. Приёмка Excel выполнена на отдельном fixture Site.
- Search data есть только одной страницы, поэтому относительный CTR benchmark отсутствует, сравнение прошлых поисковых периодов недостаточно полно. Старый uncertain Webmaster POST остаётся заблокированным. Полная очередь 690 URL необязательна и не запускалась.
- Primary Goals включают покупку, регистрацию и поиск. Оценка конверсии относится к сумме этих целей; она не доказывает потерю продаж. Для бизнес-выводов проверить состав целей и импортировать продажи.
- Существующая классификация URL эвристическая; похожие по типу страницы могут различаться по назначению. Тип можно изменить прежним действием на `/pages`, затем пересчитать.
- Drafts и история хранятся локально в БД без retention UI; wizard synchronous/bounded, для миллионов строк потребуется отдельное масштабирование. Импорт не выполняет автоматический rematch ранее несопоставленных бизнес-записей после нового scanner — нужен новый бизнес-import.
- Медианы/пороги — прозрачные MVP heuristics, не доказательство причинности и не прогноз финансового эффекта. UI не обещает рост на величину score.
- Авторизация/RBAC и отдельная приёмка полного Docker app image остаются прежними ограничениями. Sprint 4–5 отсутствуют.
