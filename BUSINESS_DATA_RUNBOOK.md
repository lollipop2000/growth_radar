# Бизнес-данные — четыре формата загрузки

Обновление Sprint 3.4: mapping содержит необязательную колонку «Кг в единице SKU», SALES — явный тип выгрузки и период покрытия. Транзакционные нули, перевод шт → кг, безопасное редактирование старых SALES metadata и обновлённые статические шаблоны описаны в [SPRINT3_4_RUNBOOK.md](SPRINT3_4_RUNBOOK.md). Приведённые ниже ограничения отсутствующих продаж и конвертации относятся к прежнему UNKNOWN/PARTIAL поведению; история и исходные записи сохраняются.

## Назначение и запуск

Страница `/business-data` доступна через основную навигацию. Четыре независимых блока: маппинг товаров, остатки, цены, продажи. В каждом — назначение, обязательные и необязательные колонки, описание/формат/пример каждой колонки, готовый XLSX-шаблон, загрузка для предпросмотра и последние десять импортов. История в БД не удаляется; универсальный `/imports` и его прежние профили сохранены.

Рекомендуемый порядок: маппинг → остатки → цены → продажи. Без маппинга загрузка для просмотра разрешена, показано предупреждение. Неизвестные SKU не записываются в BusinessRecord: видны в ошибках и отдельном счётчике истории.

Миграция `20261006130000_business_data_types` только добавляет `Import.kind` (старые записи LEGACY), `Import.unknownSkuCount` и nullable `BusinessRecord.quantity`. Старые таблицы, данные, профили и snapshots сохраняются. После остановки app/workers: `npm run db:migrate`, `npm run build`, затем `npm start`, `npm run worker`, `npm run worker:yandex`.

Локальный start и Dockerfile копируют `public` в standalone, поэтому шаблоны доступны и в production-сборке. Новый Docker image при этой приёмке не публикуется.

## Шаблоны и контракт

| Тип | Готовый файл | Обязательные колонки |
| --- | --- | --- |
| Маппинг | `public/templates/product_mapping_template.xlsx` | SKU, Групповой код, Наименование группового кода, URL магазина |
| Остатки | `public/templates/stock_template.xlsx` | SKU, Дата, Остаток |
| Цены | `public/templates/prices_template.xlsx` | SKU, Дата, Цена |
| Продажи | `public/templates/sales_template.xlsx` | Дата, SKU; хотя бы один из Заказы, Количество, Количество кг, Выручка |

Шаблоны статические: не генерируются frontend или на запрос скачивания. Первый лист `Данные` содержит заголовки и одну примерную строку. Второй лист `Описание`: название, обязательность, формат, пример, пояснение. Файлы подготовлены Artifact Tool; SpreadsheetML namespace syntax нормализован для совместимости с существующим ExcelJS reader. Содержимое и native форматы проверены повторным чтением готовых файлов.

Единый контракт UI/валидации: `src/lib/business/formats.ts`. Типизированный импорт принимает названия колонок из шаблона; порядок свободный, регистр и пробелы вокруг названий несущественны. Повторяющиеся используемые заголовки отклоняются. Дополнительные колонки сохраняются в attributesJson.

SKU и групповой код сохраняются как текст, без числового преобразования. Потерянные в исходном файле ведущие нули восстановить нельзя. Даты: ДД.ММ.ГГГГ, YYYY-MM-DD, native Excel dates. Числа: запятая или точка; все показатели неотрицательны; пустое значение не равно нулю. В каждой строке продаж обязателен хотя бы один показатель, включая известный 0. Файл до 5 МБ, максимум 20 листов, 100 колонок и 10 000 строк на листе; XLS и формулы не поддерживаются.

## Предпросмотр и подтверждение

1. Выберите файл в нужном блоке и загрузите для предпросмотра.
2. Выберите лист с данными, если первый лист не подходит. Лист `Описание` не используется для импорта.
3. Просмотрите первые 20 строк, готовые строки, ошибки, неизвестные SKU и пропуски.
4. Подтвердите импорт проверенных строк. До этого BusinessRecord не создаются.

Проверяются обязательные заголовки и значения, пустые SKU, даты, числа, дубли ключей и строк, mapping conflicts и существование SKU. Unknown SKU: «SKU не найден в маппинге товаров.». Ошибки заголовков также сохраняются в draft и видны при повторном открытии истории. UI показывает первые 100 сообщений; счётчики относятся к полному файлу.

Маппинг с ошибками не подтверждается целиком. Для остальных форматов можно явно подтвердить только проверенные строки; неизвестные SKU и другие ошибочные строки исключены. Если корректных строк нет, подтверждение недоступно.

SKU должен иметь одну актуальную строку в файле маппинга. Новая версия заменяет актуальную связь только для включённых SKU; прежние BusinessRecord остаются в истории. Один групповой код не может иметь несколько активных URL с учётом уже сохранённого маппинга. Активность — свойство связи, а не наличие товара; пустое значение означает Да. Неактивный SKU остаётся известным для исторических продаж.

Ключи дублей: маппинг — SKU; продажи — SKU/дата; остатки — SKU/дата/склад/регион/единица измерения; цены — SKU/дата/тип цены/валюта. Точные дубли также показаны как ошибки; автоматического выбора одной строки нет.

Commit повторяет проверку в существующей transaction/advisory lock. Если mapping или страницы изменились после preview, требуется повторно проверить выбранный лист. Повторное подтверждение завершённого импорта идемпотентно.

## Состояние данных и совместимость

Сводка маппинга использует последнюю версию каждого SKU, количество групп/групп с URL, уникальные нормализованные URL и сопоставление с существующими Page. Сводки остальных блоков отражают подтверждённые записи: даты, уникальные SKU, строки продаж и SKU без актуального mapping. Неимпортированные неизвестные SKU показаны отдельно в истории каждого файла.

Товарные записи связаны с Page через существующий URL matcher; новые страницы или Scanner jobs импорт не создаёт. Для остатков, цен и продаж URL, группа и название берутся из актуального mapping. Optional склад/регион/единица/тип цены/валюта сохраняются в attributesJson каждой записи.

Quantity в единицах хранится отдельно от quantityKg, доступна в dataset и Page 360. Существующее правило падения продаж RULE 10 принимает также quantity-only данные при прежних проверках покрытия периодов и стабильного трафика. Пороги и веса не изменены. Продажи агрегируются отдельно от остатков/цен; новый файл последних не замещает продажи за ту же дату. Повторная загрузка продаж заменяет текущий snapshot только для включённых SKU/дат, сохраняя остальные SKU и историю.

## Проверки и ограничения

Acceptance выполняется только на localhost fixtures при остановленных workers:

```powershell
npm test
npm run typecheck
npm run build
npm run db:status
node --env-file=.env node_modules/prisma/build/index.js migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --exit-code
npm run check:clean-db
npm start
node --env-file=.env --conditions=react-server --import=tsx scripts/acceptance-business-data.ts
node --env-file=.env --conditions=react-server --import=tsx scripts/acceptance-sprint3.ts
npm run check:localization
npm run check:secrets
```

UI acceptance временно выбирает отдельный fixture Site и восстанавливает Target Site в finally. Не выполнять одновременно с другими DB acceptance или пользовательским редактированием. Проверяется реальное скачивание всех четырёх шаблонов, загрузка/preview/commit, ведущие нули, неизвестные SKU, ошибки колонок, конфликты, stale preview, сохранение истории, идемпотентность, quantity-only продажи и мобильная ширина. Production Scanner/Webmaster jobs не запускаются. Sprint 4 не начат.

Нет конвертации валют/единиц, автоматического создания страниц и выбора между несколькими видами цен или складами для бизнес-решений. Optional metadata остаются доступны в исходных строках и истории. KPI свежести относятся к импортированным данным, не к полноте остатков/продаж во всей 1С. Для корректного анализа периодов пользователь должен выгрузить сопоставимые дни, SKU и показатели.

Итоговый отчёт приёмки: `test-results/business-data-acceptance.json`; технические проверки: `test-results/business-data-checks.json`.
